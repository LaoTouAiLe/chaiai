前端数据流与轮次展示

页面里同时存在三份"真相"：快照、流式尾部、草稿。它们各自只有一个归属，混用一处就会出现重复显示或丢字。

1 三处状态，各有唯一归属

状态放在哪为什么
会话快照、会话列表、工作区、连接 React Query（frontend/src/api/queries.ts:1-4） 服务端权威，随时可能被服务端改；页面只是缓存
选中项、每个会话的草稿 Zustand stores/ui.ts:1-10 "刷新就没了也无所谓"的东西；刻意不持久化
正在生成的那条消息 Zustand stores/stream.ts:1-5，规则在 features/conversation/streamTail.ts 它是还没进快照的那一段，不是第二份会话

三条纪律都在文件头写死了：stores/stream.ts:3-5 只做"存/取/清"，判定逻辑全在纯函数里， "容器只存结果，不藏规则——规则散了就没法单独测"；stores/ui.ts:4-5 明写"别把服务端状态搬进来"； api/queries.ts:3-4 明写事件流只做两件事：把快照写进缓存、把增量放进尾部。

2 草稿为什么按会话存

草稿是本项目里唯一"必须留"的本地状态。原因是产品裁定：任务执行中允许继续写， 切走再回来也不该丢（stores/ui.ts:6-7）。所以它是 会话 id → 文本 的映射， 而不是一个共享输入框。

  • 清空后保留键值（空串），不是删键——否则"用户删光了"和"还没有草稿"分不开，会出现"回到默认"的歧义（stores/ui.ts:19）。
  • 刻意不持久化：刷新后打开哪个会话由服务端的 is_active 决定，本地再存一份必然对不上（stores/ui.ts:9-10）。
  • 发送时草稿与引用块合并（features/conversation/quote.ts:37-40），拼好的正文才进请求。

3 流式与快照怎么合并

规则只有一句：快照是权威，增量只更新"正在生成的那条"，消息完成后按稳定的 message_id 对账（features/conversation/streamTail.ts:3-8）。 这句话被拆成三条停止条件，逐条落成了代码规则：

  1. 不靠本地 State 恢复：恢复一律来自快照，尾部只是还没进快照的那一段。
  2. 流式失败不重发用户请求：这里全是纯函数，丢尾部不发起任何请求。
  3. 不重复显示：尾部在 message_completed 到达、或快照里已出现这条完整消息时立刻丢弃（features/conversation/streamTail.ts:84-91、:113-118）。

具体的合并细节，四处值得记：

  • 增量的身份是 model_call_id#chunk_sequence。重连时服务端会把本轮历史事件再投影一次， 所以重复投递是常态：按身份丢弃，不能让同一段文字叠两遍（features/conversation/streamTail.ts:60-64）。
  • 缺块不猜：中间少了几个分片，就把服务端给到的这一段如实拼上，标记 gap， 由调用方拉一次快照补齐（features/conversation/streamTail.ts:66-70、api/useSessionStream.ts:119-122）。
  • 完成时先取快照再撤尾部：反过来会让回答在两次请求之间短暂消失（api/useSessionStream.ts:125-128）。
  • 同一轮的节点快照不能乱撤尾部：只有"出现完整消息 / 换了一轮 / 已终态"才撤， 较早的节点快照要保留正在生成的增量（features/conversation/streamTail.ts:113-118）。

传输层还有两条与"能不能重连"直接相关的约定：事件幂等只保留最近 200 个标识（有界集合，不是全记）， 以及不用 EventSource——它重连时会自动带 Last-Event-ID， 等于向服务端承诺一个不存在的续传能力（api/useSessionStream.ts:42-46、api/events.ts:5-7）。 SSE 帧还必须跨网络分片缓冲后解析，实测过一帧被切在两行之间（api/events.ts:27-32）。

4 轮次是怎么画出来的

对话页与轨迹页看的是同一份会话数据，差别只在呈现：对话把工具调用渲染成可展开卡片， 轨迹压平成表格并按轮次分组。所以轨迹不新建数据源，只摊平已经映射好的行—— "两个页签不可能各自说一套"（features/trace/adapters.ts:3-8）。

  • 一轮的边界与统计来自 TurnRecordView，由 conversation/adapters.mapTurnStats 给出，两处共用同一份锚点，不另算一套（features/trace/adapters.ts:10-12、:25-29）。
  • 轨迹里另有一份事件流水：它比消息行多两样东西——审批与压缩（这两者在消息流里没有对应行），而且有确定的先后顺序（features/trace/adapters.ts:31-36）。
  • 适配层的纪律是只搬运、不推断：契约里没有的（属于哪一轮、绑定哪次模型调用、供应商没上报的 token）在视图里保持"未知"，宁可缺不可编（features/trace/adapters.ts:7-8）。
  • 工具参数只有一种写法（key=value · key=value），对话行与检查器共用，避免用户以为是两批数据（features/trace/adapters.ts:39-44）。

5 投影为什么只回引用、不回原始字节

快照是每轮都要整份传输、整份替换缓存的东西。一旦把附件字节塞进去，恢复就变成"下载图片"。 所以投影层在三个位置刻意只给引用：

  • 用户消息的图片：只回 attachments 引用，页面自己按会话去取缩略图（application/projection.py:469-470）。
  • 多段内容：只取文本段，图像本身不在这里回给页面——"那会把 MB 级的 data: URL 塞进快照"（application/projection.py:533-538）。
  • 最终结果：只给可读摘要与证据引用，不给内部对象（application/projection.py:1957-1960）。

附带的好处是权限检查只有一处：取缩略图要走一次会话接口，服务端按同一套策略判， 而不是让每个拿到快照的客户端都握着一份字节。代价是页面要多一次请求，且断线时图片可能比文字晚到。

6 一条消息从生到死

message_started（role=assistant）
   → 建尾部 {messageId, modelCallId, text: ''}
message_delta × N（chunk_sequence 递增）
   → 拼进尾部；重复则丢弃，缺块则拉快照
message_completed
   → 先取快照，再按 message_id 撤尾部
session_snapshot（任意时刻，含重连后的第一帧）
   → 覆盖缓存；尾部与它对账：已有完整消息就丢、本轮还在跑就留

这套流程的软肋只有一个：页面里同时存在"快照的文本"和"尾部拼的文本"， 两者必须靠 message_id 对上。对不上就会出现重复显示或一闪而过， 这也是为什么对账逻辑必须是纯函数并且单独测（features/conversation/streamTail.ts:10）。

7 出问题时的表现

  • 连接类提示只有三个名字（stream_overrun / snapshot_refresh_failed / unparsable_event），且连接恢复后必须清掉，否则横幅一直挂着（api/useSessionStream.ts:48-53）。
  • 切会话导致的对账请求被取消不算故障：那是 React Query 的正常行为，当失败提示出来只会让用户看到一个莫名其妙的错误码（api/useSessionStream.ts:92-98）。
  • 断线必须可见：只在"连不上"的路径上置 reconnecting，一轮正常收尾后的 500 ms 重订阅不该让页面闪一下"正在重连"（api/useSessionStream.ts:31-37）。
未验证的部分：实际重连时的视觉表现、缺块补齐的耗时、轨迹页在长会话里的渲染性能，本轮只读源码。 验证方法：起服务后在一轮生成中断开网络十秒，看文字是否重复/断裂、横幅是否在恢复后消失； 再打开轨迹页，对比同一轮的 token 统计是否与对话页一致。
