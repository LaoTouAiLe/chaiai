移动访问与远程入口

远程访问不是"给主服务开一个端口"，而是多一个只做认证与转发的进程。主服务仍然只听回环。

1 为什么另起一个进程

远程入口是本机服务里风险最高的一块，所以它必须能被单独关掉。网关是独立进程 （python -m local_agent.mobile，mobile/__main__.py:1），不挂在主服务的 lifespan 上：它崩溃、重启、通道断开，都不影响正在跑的任务、会话与后台 worker。

  • 故障域隔离。主服务退出时按固定顺序收尾：先收网关进程树，再关运行时 （api/__main__.py 的 _shutdown）。反过来，网关先死不会带走主服务。
  • 不写业务数据。网关只有自己的状态文件——配对记录、设备授权、局域网证书， 不碰会话库、设置库与记忆。
  • 关掉就是真关掉。Windows 上把网关挂进 Job，主服务被强杀（任务管理器、IDE 崩溃） 时它也一起死（mobile/supervisor.py:172-183）。否则用户以为关了远程访问，手机其实还能连。

2 一次配对怎么完成

配对码是短期、一次性的凭据；设备 Token 只在配对那一次返回给手机，落盘只有摘要。

  • 码。主服务签发，默认 300 秒（mobile.pairing_ttl_seconds）； 命中即从列表里剔除，过期先过滤（mobile/pairing.py:194-209）。失败文案不区分 "不存在 / 过期 / 已用"，避免被当成探测信号。
  • Token。手机提交码换取；回给手机的是原文，落盘的是 sha256 （pairing.py:217）。
  • 校验。每次请求重读 pairing.json，用 hmac.compare_digest 比较摘要（pairing.py:242），不是逐字节短路比较。
  • 撤销。物理删除那条记录，旧 Token 下一次请求就是 401（pairing.py:239）。

3 网关做什么

网关只做两件事：认证，转发。业务判定一条都不复制。

动作做法为什么
认证校验设备 Token，通过后交给反代认证在网关内，与走哪条通道无关
反代逐块读写响应，不聚合正文SSE 与终端流必须边收边发（mobile/proxy.py）
改写来源Host / Origin 改写成主服务的回环地址主服务的同源校验原样生效，不给它开例外
管理接口要求"对端回环 且 Host 是回环写法"隧道进程也跑在本机，只看对端不够（gateway.py:71）

4 三条通道

通道怎么暴露状态
lan本进程多开一个监听：自签证书 HTTPS，或明文 HTTP已实现
tailscale让外部命令反代到网关回环端口：serve 仅 tailnet，funnel 公网已实现
cloudflared—未实现：配置里启用会直接报错并拒绝启动

5 边界

  • 默认关闭。关闭状态不起进程、不占端口、不写文件；配置校验只在 enabled: true 时才要求完整参数。
  • 每通道独立。独立开关、独立配对、独立设备授权——局域网授权不等于远程授权。
  • 凭据只存摘要。Token、配对码都不落明文；管理页只下发设备 id、名称、通道与时间。
  • 明文是可选项，代价要写清。lan 的 tls: false 让手机"打开就能用"， 但同网段的其他人可以在链路上看到通信内容。
