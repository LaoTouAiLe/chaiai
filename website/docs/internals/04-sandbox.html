写侧沙箱与权限判定

档位回答的是"能写到哪"，判定则分三层做：解析路径、查受保护目标、交给内核。三层各自失败闭合，谁也不替谁兜底。

1 三档是什么语义

档位在 2026-10-15 从"工作区外能不能读"改成了边界语义：三档都允许用显式绝对路径读取本机目标， 差别在能写到哪（security/path_guard.py:42-48）。

档位（界面 / 代码值）文件工具命令写边界（Windows）
只读
read-only		 连工作区都不许写：写类工具一律拒绝，且不是"等审批"（security/policy.py:683-697）。 以无任何写授权的受限令牌运行：读得到、写不进去（security/policy.py:421-430）。
工作区可写
workspace-write
（出厂默认）		 工作区内正常读写；外部默认只读，写要逐条 read_write 授权。 可写范围 = 工作区根 + 该工作区专属临时目录 + 用户授权的「读写」目录（security/policy.py:392-396、security/policy.py:431-458）。
常规免审
danger-full-access		 工作区可写，外部一律可读；写仍只按逐条授权（security/path_guard.py:48）。 同样受写边界约束，写法与工作区可写一致（src/local_agent/api/routes.py:1022-1024）。

旧值 deny / whitelist / allow 仍被接受并归一 （security/path_guard.py:50-62）：设置库里存着旧值，硬拒绝会让老用户开不了机。 但认不出来的值不静默兜底，直接报错——否则一个拼错的档位会落成默认档， 而默认档恰好不是最严的那一档（security/path_guard.py:65-70）。

2 一次写入要过四道判定

顺序写在 resolve_writable_path 里，四步都在同一个函数内，不能跳（security/policy.py:618-633）：

  1. 解析目标。相对路径按工作区展开后 resolve() 再校验一次边界，所以"工作区内指向工作区外的软链接"也会被拦住（security/path_guard.py:5-9）。工作区外只认原始输入就是绝对路径；~、相对路径逃逸与 Windows 盘符相对路径一律拒绝（security/path_guard.py:359-374）。
  2. 敏感文件。按文件名模式拦，block_known_secret_files 打开时命中即拒（security/policy.py:626、security/policy.py:1062-1064）。
  3. 受保护目标。根目录、主目录、.git、凭据目录、系统关键目录——不可审批，换谁批都不执行（security/policy.py:524-533）。
  4. 档位与访问级别。只读档直接拒；外部目标只有 read 权限时，提示去设置里改成「可读写」（security/policy.py:628-632）。
顺序不是随意排的：受保护目标排在档位之前，因为"这个档允许写"和"这个目标能不能写"是两个问题； 反过来的话，最宽的档位会把根目录变成可写目标。同理，敏感文件也排在档位之前——最宽的档不该让密钥变成可读文本。

3 外部写入：只读、读写、不可审批

外部目标的副作用统一走一个判定入口（security/policy.py:759-790），结论只有三种：

  • 只有只读权限（或最宽档下没有逐条授权）→ 硬拒绝，不经审批。理由是"问一次就能写"会让人误以为工作区外写是个可选动作，而实际语义是"先授权才能写"（security/policy.py:766-771）。
  • 有读写授权 → 视同工作区内，交给各工具自己的风险规则（覆盖、删除等仍按第 3 章那些判据走）。
  • 受保护目标 → 无论哪档、无论是否授权，一律硬拒绝。

有一层容易被忽略：凭据目录即使落在可写范围内也始终不可写。授权一个目录的意思是"用户认可在那里干活"， 不等于把 .aws/credentials、.ssh/id_rsa、.kube/config 一起交出去， 所以这六个目录与 .git 同级、不可审批（security/path_guard.py:88-107）。 只收确属凭据的目录：.config、.npm、.cache 这类太常见，收进来会误伤普通文件。

敏感文件名清单同理，只匹配文件名、不匹配目录名。清单里 mcp.json 是端到端验证时加进去的： 真实模型确实用 read_file 打开过它，只是没把里面的明文凭据说出去——不能靠这个运气 （security/path_guard.py:137-156）。

4 Windows 的写侧沙箱做了什么

模块的定位一句话：受限令牌、逐可写根 SID、目录 ACL 与 Job Object（security/win_sandbox.py:1）。 它不是"读隔离"，也不假装是。

  • 令牌用 TokenGroups 里的真实登录 SID 做限制列表，绝不携带 TokenUser；DefaultDacl 给登录 SID 授予内核对象访问权，否则去掉用户 SID 后连 DLL 初始化都失败（security/win_sandbox.py:3-5）。
  • 每个可写根一个 v3 SID：撤销授权或降为只读后，下一轮令牌不再携带旧 SID（security/win_sandbox.py:6）。
  • 根上是一条可继承的"读+写" ACE，新目录立即继承可写；只给写会让工作区在"ACL 没显式列当前用户"的目录上连 dir 与跑测试都做不了（security/win_sandbox.py:11-16）。
  • 物化失败阻止执行：可写根授权不了、或受保护子树的拒绝项建不起来，就不跑——不拿继承来的允许项凑合（security/win_sandbox.py:19-21、security/policy.py:448-451）。
  • 临时目录：把 TMP / TEMP / TMPDIR 指到该工作区专属目录，否则很多命令会因为写不了临时文件而成片失败（security/policy.py:453-455）。

已知边界写在模块头部，读的时候不要跳过（security/win_sandbox.py:23-29）：

  • 读侧与网络不隔离；
  • Everyone 或登录 SID 本身已有写权限的对象仍可能可写；
  • NTFS 硬链接、并发改名不提供路径级强隔离；设备对象不受目录授权控制；
  • FAT 等不支持 DACL 的卷：根授权失败即拒绝执行；
  • 首次扫描之后新建的凭据子树不会即时获得拒绝项，要等下次进程启动——不是按名字实时隔离。

5 非 Windows：照常跑，但说清楚

没有 OS 级写边界时，不再失败闭合，而是照常运行并给出一句如实说明： "路径工具受档位策略限制；命令内部的文件访问不能由路径工具约束，不是内核强制" （security/policy.py:373-384）。静默跑掉等于假装有边界，那正是移植笔记里点名的 fail-open 坑。

6 授权记录存在哪

档位是设置库里 settings_meta 的一行，逐条授权在 external_path_grants 表 （persistence/migrations.py:253-268）。授权不写回 config.yaml： 让应用改自己的配置文件会抹掉注释，在只读挂载上还会直接失败。主键存规范化路径， 这样 E:/data 与 e:\data 落到同一行，否则"授权过却仍被拦"只能靠肉眼比对路径才查得出 （persistence/migrations.py:259-261）。

  • 档位与授权每轮现取，所以改完从下一轮生效；正在跑或等待审批的那一轮保留提交时的档位（src/local_agent/application/service.py:3947-3950、src/local_agent/api/routes.py:1020-1024）。
  • 写授权不代替覆盖、删除这类逐次审批（src/local_agent/api/routes.py:1035-1038）。
  • 同一个目标重复授权是改写访问级别，不是加两行；撤销写授权不影响默认读取（src/local_agent/api/routes.py:1040-1041、src/local_agent/api/routes.py:1054-1056）。
  • 没有可用设置库时不报错：返回出厂默认并标 store_unavailable，页面上写清"这里改了也存不下来"（src/local_agent/api/routes.py:1006-1011）。

7 三层为什么不能合并

解析层回答"这是哪个真实目标"，策略层回答"这个目标该不该动"，内核层回答"这个进程有没有权限动"。 任何一层被跳过都会出问题：只靠内核，读侧没有隔离也没有敏感文件概念；只靠策略，命令内部的文件访问就没人管； 只靠解析，就没有撤销与授权这回事。

这也是为什么"工作区可写"这句话在文档里一直写成授权而不是承诺：脚本在工作区里删了什么， 解析层看不见。

未验证的部分：受限令牌与 ACL 的实际效果、FAT 卷与硬链接的边界、非 Windows 的失败表现， 本轮只读源码，没有在本机做隔离验证；模块自己也不承诺其他机器的扩展模块兼容性（security/win_sandbox.py:27-28）。 验证方法：在工作区外建一个目录、不加授权执行 write_file，应看到指向「设置 → 权限」的拒绝； 再授权为可读写后重试，应成功且命令写其它外部目录仍失败。
