架构总览：两层界面与一支执行链

页面只发请求，判定留在服务端，状态落在同一个 SQLite。这三件事定下了后面每一章的形状。

1 一次追问走过哪几层

整条链只有一支：浏览器发请求，服务端跑图，工具落盘。中间没有第二个服务，也没有第二个进程。 

浏览器（React 页面）
  │  相对路径 /api：JSON 请求 + SSE 事件流
  ▼
FastAPI 入口          api/app.py:61          create_app 是唯一装配点
  │  本机边界：Host / Origin / 正文上限
  ▼

  │  幂等台账 → 预检 → 执行锁 → 跑图 → 投影
  ▼

  ▼
工具与安全策略        security/policy.py:3
  ▼
本机磁盘 + SQLite（Checkpoint、会话索引、幂等台账）

2 界面为什么不碰文件

界面是浏览器里的 React 页面，它的全部能力就是发 HTTP 请求和读 SSE 事件。这不是自觉，是结构决定的。

  • 同源托管。前端构建产物由本服务自己发：api/static.py:3 写明"生产环境只需要启动 Python"， 兜底路由在业务路由之后注册（api/app.py:132-137），所以页面和接口同源，不存在跨端拼地址的余地。
  • 只走相对路径。传输层客户端只认 /api，从不拼绝对地址， 因此请求不会跑到用户没配过的机器上（frontend/src/api/client.ts:6-8）。
  • 判定不在这一侧。危险动作在代码层拦，不依赖 Prompt（security/policy.py:3-4）； 没放行或没有审批能力的动作一律失败闭合。把判定交给页面，等于把闸门交给请求方。
  • 类型是生成物。前端类型由服务端 OpenAPI 生成，生成文件不得手改（api/app.py:40-42、 frontend/src/api/client.ts:1）。接口改了而页面没跟上，是编译期错误，不是运行时惊喜。
界面负责服务端负责
把输入变成一次请求，带上幂等键判定这次请求是谁、能不能跑、跑没跑过
把 DTO 渲染成话题、轨迹、审批卡把 State 投影成 DTO，只回引用与结论
展示"断线了""正在重连"决定这一轮的终态，写下台账
从不重发用户消息，重试由人发起同 id 同参数的重试直接回放，不再跑图

3 四层职责

按依赖方向从外到内，每层只做一件事；跨层的调用方向单一，不回头。

层目录只负责明确不做
接口层 api/ 路由、本机边界、SSE 帧、静态托管 不判业务，不读写 State
应用层 application/ 幂等台账、执行锁、跑图、把 State 投影成 DTO 不决定某个工具能不能放行
图与工具层 graph/、tools/ 按节点推进一轮、执行工具、写审计字段 不知道 HTTP，也不知道页面
支撑层 security/、persistence/、context/、memory/、llm/、mcp/、rag/ 判定、存储、提示组装、模型适配、外部工具目录、按需检索 不自己发起轮次

persistence/ 只有一句话的定位："Checkpoint 与会话索引"（persistence/__init__.py:1）； context/prompt_context.py:1-11 则把提示拆成"稳定前缀"与"动态快照"两块，前者在同一会话内字节不变。 这两处约束会直接影响第 5 章的压缩策略。

4 图里有什么

图在 graph/builder.py:119 构建，注册了 18 个节点（graph/builder.py:135-152）与 3 个固定子图（graph/builder.py:153-155），最后 compile 并放开递归上限（graph/builder.py:157）。 边的形状写在 graph/edges.py:85-182，文件头有一份可直接读的路径图。 节点按什么顺序串起来、在哪个节点上分叉，留给第 2 章。

5 单进程、单 worker 是硬约束

入口把 workers=1 写死（api/__main__.py:160-167），并说明这不是懒得配： 进程内广播、每会话互斥与幂等台账，都以"只有一个进程在写"为前提（api/__main__.py:17-18）。 想开多进程，先要换掉这三样的实现，而不是改一个启动参数。

服务只为本机设计：监听非回环地址时只打印一条警告，没有鉴权（api/__main__.py:100-106）； FastAPI 自带的交互文档也刻意不挂（api/app.py:93-95），避免多开一个无鉴权的调试面。

6 状态放在哪

Checkpoint、会话索引、幂等台账、任务索引共用同一个 SQLite 库、同一条连接、同一把锁 （api/container.py:242-290）。图在 api/container.py:250 拿到这个 checkpointer； 库打不开就没有会话可服务（api/container.py:224）。

库文件位置由数据根推算，优先级是"环境变量 → 指针文件 → 配置里的 data_root → 平台默认" （app_paths.py:214-215，环境变量名与指针文件名见 app_paths.py:83、app_paths.py:87）。 服务启动时总会把实际数据根打出来（api/__main__.py:124-126），因为它是备份、迁移与排障的唯一锚点。

投影层是单向的：输入 State、输出 DTO，不写回、不调用模型、不读数据库 （application/projection.py:1-5）。这条纪律让"页面显示的状态"永远可以追到某个 Checkpoint， 而不是某一处顺手改的缓存。

7 这套划分的代价

  • 改前端必须重新构建。服务端只按目录内容返回文件（api/static.py:154-164）， 它不关心产物是否与源码同步；不重建，页面就还是旧产物。产物缺失时只提供接口并给一句可执行的提示 （api/static.py:88-93）。
  • 加一个能力要同时改两端。服务端加路由与 DTO，前端重新生成类型，少一边就编译不过。
  • 没有鉴权。本机边界只挡跨源与 DNS rebinding（api/security.py:1-17）， 挡不住同机上的其他进程。这是"只在本机用"的设计，不是可以对外开放的服务。
