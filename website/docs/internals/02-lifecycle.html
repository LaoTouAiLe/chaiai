一轮请求的生命周期

从一次提交到页面看到终态，中间是七个固定环节。哪些能重试、哪些只能人工核对，由它们各自失败时落在哪里决定。

1 七个环节

以下行号都在 application/service.py，除特别标注的文件。

#环节位置这一步失败时
1 幂等判定 service.py:3149-3156 同 id 不同参数 → 冲突；同 id 同参数 → 直接回放原结果，不再跑图
2 抢执行锁 service.py:3158-3165 同会话第二次提交 → 会话忙
3 陈旧台账核对 service.py:3168-3170 台账说“执行中”但锁空闲（上一次进程留下的）→ 只读核对，绝不自动重跑
4 预检 service.py:2949-2985（定义）、service.py:3171-3172（调用点） 解析连接、备客户端、读附件；失败即返回，且不留“执行中”记录
5 落台账 service.py:3173-3182 写一条“执行中”，此后崩溃都会留下可核对的痕迹
6 跑图 service.py:3389-3419 异常 → 保留“执行中”并标记需要恢复（见第 7 节）
7 收尾投影 service.py:3282-3299 台账落终态，再发最后一批事件；终态必须是最后一条

顺序写在一处说明里：台账（冲突/重放）→ 抢锁 → 陈旧台账恢复 → 执行前校验 → 落台账 → 跑图 （application/service.py:3135-3147）。改动其中任意两步的先后，都要先读那段注释。

2 提交返回的是引用，不是结局

POST /api/sessions/{id}/messages 是同步接口：这一轮跑完才返回，返回的是稳定的命令结果引用， 结局不依赖 SSE（api/routes.py:705-719）。所以页面断线不会让这一轮“没发生”。

幂等键的摘要把附件一起算进去（application/service.py:2930-2938）：否则“同一段文字、换一张图再发” 会被判成同一次请求，图永远发不出去。这是被真实故障逼出来的一条。

3 预检为什么不能晚一步

预检（解析连接、备好客户端与密钥、读附件）必须排在落台账之前。 如果先写“执行中”再发现没有可用连接，这条请求什么都没跑却留下了记录； 用户按提示配好连接、拿同一个请求 id 重试时，会被当成上一次进程留下的陈旧请求，判成需要人工核对 （application/service.py:2950-2955）。预检失败还会把自己的取消意图一起复位， 所以它也不会顺手清掉上一轮的状态（application/service.py:2984-2985）。

另一头也有闸：审批还没决定时不允许开新一轮，因为直接跑新输入会把挂起的审批丢掉， 让“等待授权的操作”无声消失（application/service.py:3096-3102）。

4 图里的顺序

graph/edges.py:5-22 的文件头就是这张图，摘其中主干：

START → prepare_context → load_agents → recall_memory → mode_router
mode_router --chat--> compression_node → chat_node → reflection_node → completion_router
mode_router --tool--> retrieve_code_node → planner_node → compression_node → agent_decision_node
agent_decision_node --有工具调用--> safety_gate_node
safety_gate_node --有放行调用--> tool_execution_node → reflection_node → completion_router
completion_router --continue--> planner_node（新循环）
completion_router --finish/ask_user/loop_limit--> final_response_node → END

第一个节点负责把“本轮”的字段全部复位（循环计数、任务目标、计划、待执行调用、挂起审批等）， 否则多轮工具任务会累计到循环上限（graph/nodes.py:304-312）。它只在新请求时执行， 审批恢复从断点继续，不重跑这里（graph/nodes.py:308-311）。

上下文在进入模型前分成两块：稳定前缀（核心身份、模式规则、工作区根、项目规则、工具规范） 在同一会话内字节不变；动态快照（模式理由、当前目录、会话摘要、召回记忆、代码片段、当前任务与计划） 按固定顺序序列化后注入（context/prompt_context.py:3-10）。前缀稳定是缓存命中率的前提， 也解释了第 5 章为什么压缩不能改写原始记录。

5 工具循环与审批挂起

  • 放行与否由安全门判定（graph/tool_runner.py:134）；工具注册表只负责“有哪些工具、给谁看”，不是授权（tools/tool_registry.py:1-5）。
  • 需要人工批准时进审批节点；该节点在恢复时会被整体重放，因此 interrupt() 之前不允许有任何副作用（graph/tool_runner.py:841-846）。
  • 递归删除要两次独立恢复：第一次恢复推进阶段，第二次独立的 interrupt() 返回“批准 + 显式二次确认”才授权（graph/tool_runner.py:842-845、graph/tool_runner.py:866-877）。
  • 无人值守会话（定时任务、心跳、子 Agent）不会挂起：没有人能点批准，挂起来会永远停在等待审批（graph/tool_runner.py:853-862）。
  • 恢复不是重新提交，而是给图一条 Command(resume=...)，并接上原来那个等待中的任务（application/service.py:3028-3092）。

6 投影：边跑边发，终态最后一条

_execute 的说明是“边跑边投影”：每完成一个节点就 flush 一次，把自上次以来新增的事实发出去 （application/service.py:3243-3260）。不加这一步，接上 SSE 也只能在收尾时看到“刚刚发生了什么”， 看不到执行中的工具与计划（application/service.py:3231-3234）。

  • 执行期的 flush 明确不带终态（include_terminal=False），终态在收尾那一次单独发（application/service.py:3292-3299）。
  • SSE 的事件名就是事件类型，data 是完整信封，前端可以直接按生成的类型解析（api/sse.py:49-55）。
  • 三种非业务结束都显式告诉客户端：落后太多、空闲超时、心跳（api/sse.py:69-112）。
  • 页面侧的重连先取快照，再订阅增量；失败只重连订阅，从不代用户重发消息（frontend/src/api/useSessionStream.ts:3-9）。

7 中断、恢复与“结果不确定”

台账只有三个状态：执行中、成功、失败；只有后两个是终态，可以直接拿结果（persistence/request_ledger.py:21-27）。

  • 用户取消是幂等的，且不进幂等台账：重复调用本来就是空操作， 记一条“执行中”反而会污染“同一请求 id 的重试”语义（application/service.py:807-812）。
  • 异常发生在副作用之后时，终态是不确定的。代码不写“失败”， 而是保留执行中并标记需要恢复，因为写“失败”等于声称“什么都没发生”，下一次同 id 重试会直接拿这条结论走人 （application/service.py:3264-3275）。
  • 恢复只读核对：能证明终态就补齐结果引用、按重放返回；证明不了就要求人工核对，绝不自动重提 （application/service.py:3466-3499）。证明的前提是台账绑定的 run_id 与 Checkpoint 当前那轮相同—— NULL 表示“不知道”，不是通配符；把“不知道”当匹配，正是“重试拿到别人结果”的来源（application/service.py:3470-3472）。
  • run 的绑定必须早于副作用。所以跑图用 stream 而不是 invoke： 图一交出 run_id 就写台账，那时第一个节点还没开始调模型（application/service.py:3340-3346、application/service.py:3402-3416）。
未验证的部分：事件的实际时序、跨轮压缩的触发时刻、真实模型长会话下的恢复表现——本轮只读了源码， 没有启动服务观察，因此这些只算推断。验证方法：起服务后用浏览器开发者工具看 /api/sessions/{id}/events 的帧序列， 并在一个长会话里对照 Checkpoint 与台账的 run_id。
