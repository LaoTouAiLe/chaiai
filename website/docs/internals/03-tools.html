工具层与安全判据

注册表只管"有哪些工具、给谁看"，放行由安全策略判。两件事分开，是因为任何一次漏登记都会变成一条静默的执行通道。

1 三张表决定一个工具能不能跑

一个工具从"已实现"到"模型真能调起来"，要过三张表。三张表都不在同一个文件里，这是刻意的： 每张表负责一个不同的问题，混在一起就会出现"注册了就等于授权"。

表位置回答什么对不上时
能力归属 capabilities.py:49-53 这个工具属于哪个能力（files_read、shell、mcp…） 构造注册表时直接抛错（tools/tool_registry.py:187-223）
运行期开关 capabilities.py:10-11 本次运行的能力集合是什么 能力不进集合，工具拿不到 schema
放行清单 security/policy.py:106-113 这个工具允许执行吗、要不要人工批准 安全门按"未登记"拒绝（security/policy.py:730-734）

能力归属的校验是双向的：能力表里有但没实现，报错；实现了但没登记能力，也报错 （tools/tool_registry.py:213-223）。理由是这类错误只会以"模型怎么从来不用这个工具"的形式 很久以后才暴露（tools/tool_registry.py:100-102）。

外部工具（MCP）是这套闭集唯一的开口，代价用三条约束压住：名字必须带 mcp__ 前缀、 只能归到 mcp 能力、不得与静态登记的工具重名（capabilities.py:29-39）。

2 判定落在安全门，不落在工具里

每个待执行的调用先过安全门（graph/tool_runner.py:134-140）。门里只做两件事： 先看这个工具在不在本轮的可见集合里，再交给策略判定（graph/tool_runner.py:160-184）。 "没绑定给模型"必须同时是"不能执行"，否则模型自己报个名字就能跑（graph/tool_runner.py:172-174）。

classify_tool 的判定顺序就是优先级，从高到低（security/policy.py:637-734）：

  1. 已取消 → 拒绝。取消走的还是这个方法的拒绝出口，不新开旁路（security/policy.py:645-652）。
  2. 控制类工具（改计划、任务生命周期）→ 放行（security/policy.py:653-654）。
  3. 持久会话与浏览器 → 按工作区可写与目录授权判（security/policy.py:655-675）。
  4. 只读工具 → 放行（security/policy.py:676-682）。
  5. 只读档下所有写类工具 → 拒绝，且不是"等审批"（security/policy.py:683-697）。
  6. 写文件、下载、执行代码、Shell、Git 提交、删除 → 各自的细分判定（security/policy.py:698-727）。
  7. 其余 → 未接入或不在清单内，拒绝（security/policy.py:730-734）。
为什么"只读档拒写"要写在一处：它放在各类工具的判定之前，是为了让 "这个档位下不能写"只有一个出口——漏掉一个工具就是一条静默的写通道。这里刻意让 requires_approval=False：没有批准能把它放行（security/policy.py:688-696）。

3 拒绝与"等审批"是两回事

判定结果里有三个字段：allowed、requires_approval、reason， 外加一个 reason_kind（security/policy.py:131-143）。 reason_kind 区分"策略不放行""环境里起不来""参数不符"——因为把 "这台机器没装这个命令"显示成"被安全策略拦截"，会让人去改一个不需要改的设置。

  • 硬拒绝：不弹卡，也没有批准能救。越界、受保护目标、只读档写文件都属于这类。
  • 需要审批：弹卡，批准后执行；拒绝按动作指纹记账，模型换个 tool_call_id 也绕不开。
  • 本轮拒绝过就不再问：作用域是本轮，不是永久——早先跨轮永久生效时，"拒绝过一次时间命令"会让此后每次问时间都直接失败、连卡都不弹（graph/tool_runner.py:186-201）。
  • 已经批准过的同一次调用（异常后重放）直接沿用批准，不重复问（graph/tool_runner.py:203-219）。
  • 一次只问一个：一排待审批动作只弹第一张，其余排进 deferred_tool_calls 且不产生任何结果——它们还没有结局；批准并执行完第一张后，流程回安全门接着问下一个（graph/tool_runner.py:237-253）。

4 破坏性命令名单为什么只能追加

Shell 的主判定是解析后的命令结构，黑名单只作最后兜底（security/shell_guard.py:3-9）。 但兜底必须由代码保证：出厂配置里的 security.shell.blocked_patterns 默认是空列表， 只靠用户自配的话，"破坏性命令必须人工批准"这条约束在出厂状态下等于没有落地—— "常规命令免审"一开，format C: 就会直接执行（security/shell_guard.py:117-122）。

  • 底线清单写在代码里：DESTRUCTIVE_PATTERNS（security/shell_guard.py:126-155），覆盖删除、磁盘与引导、关机与杀进程、权限与注册表与计划任务。
  • 配置只能追加，不能取消；匹配时先查用户配置、再查代码底线，配置命中的措辞更贴近用户语境（security/shell_guard.py:670-678）。
  • 短名字带尾随空格并要求左侧名称边界，避免把 reformat、model 这类误判（security/shell_guard.py:124-125）。
  • 对称的一面：已知只读命令有代码层免审清单，否则"问个时间都要弹卡"（security/shell_guard.py:158-179）。

5 哪些工具可以并行

并行按工具契约逐个列举，不按"只读能力"泛化：delegate_research 会启动子任务、 read_shell 会推进日志游标，它们"只读"，但不能并行 （graph/tool_parallel.py:18-24）。

  • 白名单只有 list_dir、read_file、grep、glob、web_search、web_fetch、Git 只读三件套、技能清单与正文、view_image、inspect_system（graph/tool_parallel.py:20-24）。
  • 带 save_full 的 grep / glob 不并行：它们会落盘，落盘与额度计数仍走串行路径（graph/tool_parallel.py:32-33）。
  • 执行侧还有四道附加条件：未执行过、不在本轮审批名单里、不是遗留的副作用动作、当前可见（graph/tool_runner.py:421-431）。
  • 只并行工具调用本身，不在线程里合并 Graph 状态或操作 Checkpoint（graph/tool_parallel.py:1、graph/tool_parallel.py:51-64）。
  • 串行与并行批次的结果汇到同一个记账点，再统一进上下文预算（graph/tool_runner.py:690-695）。

6 这一层管不到的地方

  • 命令模式识别不了脚本内部的动作。判定基于解析后的命令结构（security/shell_guard.py:3）， 一条 python clean.py 内部删了什么是看不到的。这也是为什么"工作区可写"是授权，不是承诺。
  • MCP 免审批是权衡，不是疏忽。一台 server 的 command 由用户亲手写进 mcp.json， 调用它等于使用已授权的东西；早先"一律审批"的实测结果是模型连着调几个工具就要点几次卡， 人很快就不再读卡片直接点批准——那比不审批更糟（security/policy.py:736-750）。 边界仍在：只读子任务拒绝、名字必须来自本轮已知集合。
未验证的部分：并行的实际收益、审批卡在多动作场景下的交互节奏，本轮只读了源码， 没有起服务实测。验证方法：让模型在一轮里连发多个 read_file，对比耗时与事件顺序； 再发一组删除 + 写入，观察是否只弹第一张卡、批准后是否继续问下一个。
