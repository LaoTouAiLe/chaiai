测试与验收方式

替身模型管"行为对不对"，真实模型管"能不能用"，人工验收管"装到机器上还活着吗"。三层不互相替代，也不能互相背书。

1 三层，问的是三个不同的问题

层用什么模型默认跑吗断言什么
自动化层 脚本化替身（tests/conftest.py） 跑，属于常规回归 终点类型 + 几条必须为 0 的硬不变量（tests/test_agent_eval.py:14-22）
冒烟层 真实模型 不跑，DS_SMOKE=1 才跑 只记录兼容性与质量，不做逐字断言（tests/test_agent_smoke.py:1-8）
精度层 真实模型 不跑，DS_PRECISION=1 才跑 硬阈值，但取总体下限（tests/test_agent_eval_precision.py:1-30、:104-110）

规模参考（会随代码变化）：后端 tests/ 下 146 个 .py 文件（含 conftest.py）， 前端 src/ 下 62 个 *.test.ts(x)，由 npm run test（vitest）执行； 前端构建 npm run build 先跑 tsc --noEmit，类型错误进不了产物。

2 替身为什么能当基准

假模型按提示内容区分两类调用：路由分类返回分类 JSON，其余按配置返回工具调用或文本回答—— 两条链路都能断言，且不联网、不依赖真实模型输出（tests/conftest.py:1-5）。 三点让它称得上"基准"而不是"凑数的桩"：

  • 流式与非流式同一套脚本：增量块拼起来必须等于整段回答，所以两条路径的最终消息完全一致（tests/conftest.py:345-350）。
  • 每个用例一个独立数据根：不隔离的话，跑测试会直接读写用户真实的会话库与设置库，用例之间还会互相串（tests/conftest.py:32-49）。
  • 它明确承认测不到什么：替身能测终点与安全不变量，测不出"模型有没有真的引用行号"——那正是精度层存在的理由（tests/test_agent_eval_precision.py:1-11）。

3 自动化层盯的四条"必须为 0"

指标里有两类：可以波动的比例，和一条都不许有的红线（tests/test_agent_eval.py:16-22）：

  • 错误宣称 = 0：任务标 completed 但产物或执行证据不符。
  • 重复副作用 = 0：同一次任务里同一副作用工具执行超过一次。
  • 密钥 / 越界泄漏 = 0：轨迹或出站提示里出现工作区外内容与密钥。
  • 轨迹含隐藏思维链 = 0：决策轨迹、工具事件、错误事件、最终证据里不得出现 reasoning_content。

比例类指标是完成率与追问率：追问不一定是错，要看原因分布（tests/test_agent_eval.py:16-17）。 结果写成固定报表 eval/latest.json / eval/latest.md，两次运行可直接对比（:1-5）。

4 真实模型这一层怎么控成本

默认不跑，理由直接写在 skipif 的 reason 里，而不是写在某个人的记忆里： "要联网、有费用、输出不稳定：显式设置 DS_SMOKE=1 才运行" （tests/test_agent_smoke.py:530-533）。精度层同理，开关是 DS_PRECISION （tests/test_agent_eval_precision.py:725-728）。

  • 冒烟层只记录、不打分：文件头自己写明"默认跳过、只记录不比对"（tests/test_agent_smoke.py:1）。
  • 精度层不按单条硬断言：真实模型同一用例两次运行可能一次收尾、一次追问，单条 flaky 会让门槛随机变红， 而随机变红的门槛等于没有门槛；所以改成总体下限，系统性退化仍然会红（tests/test_agent_eval_precision.py:105-110）。
  • 离线报表用字段自证没花钱：paid_model_calls == 0、semantic_quality_reviewed is False、 real_model_advantage_proven is False（tests/test_workflow_eval.py:59-63、 tests/test_workflow_comparison.py:18-24）。这三个字段的意义是：离线跑出来的结论不能写成真实模型的结论， 否则下一个人会把"替身证明"当成"真机证明"。

5 只跑 pytest 不够：还有五道离线门

  • 兼容基线：默认只读检查，--write 只在审查契约后显式使用（scripts/check_release_contracts.py:1-2、:20-34）。
  • OpenAPI 与偏好 schema 的导出：生成物必须与代码一致，用各自的 --check 守。
  • 规模与复杂度棘轮：文件行数、函数行数、圈复杂度、嵌套深度四个门槛，基线只存超标项， 新超标和存量恶化都失败（scripts/check_size.py、tests/test_code_size.py:80-84）。
  • 交付证据离线复核：校验冻结的证据文件，从不调用模型（scripts/verify_delivery_evidence.py:1）。
  • 固定工程评测：输出到新目录、拒绝覆盖旧结果，源文件指纹与契约清单随报告保存（scripts/run_release_evaluation.py:1、:20-32）。

另外有几条评测脚本本身就是"不花钱"的：离线基线明确"不创建真实模型客户端" （scripts/run_workflow_baseline.py:1），固定工程评测"不触发付费模型" （scripts/run_release_evaluation.py:1）。

6 跳过不是通过

测试里条件跳过很常见，但这里要求它如实标注，不假装跑过。最直白的一条写在进程树用例上： "非 Windows 上跳过并如实标注——不假装跑过"（tests/test_process_guard.py:281-285）。 跳过的四类原因，读报告时要分开看：

  • 平台语义：POSIX 权限位、Windows ACL 与受限令牌、junction、大小写规则（tests/test_tools.py:370、tests/test_permission_model_review.py:17、tests/test_external_read_policy.py:127）。
  • 可选依赖：中期记忆需要 uv sync --extra memory，没装就跳过而不是失败（tests/test_memory.py:86-92）。
  • 环境能力：跨盘验证要求临时目录在另一块盘、符号链接需要创建权限、缺少 git / node / python 时直接说明（tests/test_external_read_policy.py:147-153、tests/test_protected_scan.py:102-104）。
  • 真实模型开关：见上一节。

所以看一份报告时，"passed 多少"不足以判断验收状态；必须同时看用 -rs 打出来的跳过原因—— 跳过的用例意味着这条结论在你这台机器上还没有证据。

7 哪些结论只能由真机或真实端点证明

  • 行号级引用准不准：替身回放测不出真实模型会不会真的引用 文件:行号（tests/test_agent_eval_precision.py:7-11）。
  • 协议级兼容性：工具调用格式、流式分块、结构化输出的降级链，只有真实端点能暴露； 冒烟层的定位就是"发现协议级/兼容性问题"，不是打分（tests/test_agent_eval_precision.py:9-10）。
  • 平台安全能力：受限令牌、目录 ACL、junction 重定向、进程树终止，只在对应平台上成立，别的平台是 skip（tests/test_permission_model_review.py:17、tests/test_process_guard.py:281-285）。
  • 成本与缓存：离线只能算估算值，真实命中率与回落次数要看供应商回报（见第 5 章的验收观测量）。
  • 安装器与桌面窗口：仓库的测试与脚本里没有引用安装器脚本（chaiai.iss / ISCC）的用例， 这两件事只能按"编译 → 隔离环境安装 → 启动 → 核对实际读写位置"人工验收，不能拿 pytest 全绿顶上。

8 提交前最小闭环

# 后端（在 local-agent-web/ 下）
.venv/Scripts/python -m pytest -q            # 含规模棘轮的常规回归
.venv/Scripts/python -m ruff check .
.venv/Scripts/python -m mypy src

# 前端（在 local-agent-web/frontend/ 下）
npm run typecheck
npm run test
npm run build                                # 产物要给服务端托管，不重建就是旧页面

# 契约与证据（在 local-agent-web/ 下）
.venv/Scripts/python scripts/check_release_contracts.py --check
.venv/Scripts/python scripts/export_openapi.py --check
.venv/Scripts/python scripts/export_preferences_schema.py --check

真实模型的两层不在这条闭环里：它们要联网、要花钱，得显式开开关，且结果只写"记录"不写"通过"。

未验证的部分：本章只读源码与脚本，没有运行任何测试——所以文中没有给出通过数， 也不代表当前工作树是绿的。要验证本章的说法，跑一次 pytest -rs 看跳过原因是否与第 6 节列的四类对得上， 再跑一次 npm run test 看前端 62 个测试文件是否都能被收集到。
