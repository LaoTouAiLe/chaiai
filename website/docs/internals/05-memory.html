记忆与上下文压缩

记忆回答"下一轮还记得什么"，压缩回答"这一轮能带多少"。两者共用一条规则：Checkpoint 是原始记录，压缩不删不改。

1 五块东西各存什么

项目里说"三层记忆"指的是短期（Checkpoint）、中期（向量）、长期（结构化）；实际进提示的还有两块： 会话摘要与常驻记忆。五块的载体、时机都不同，混在一个"记忆"里谈必然出歧义。

块载体写回到提示
Checkpoint（短期） LangGraph State，落 checkpoints.sqlite（config.py:281-290） 每个节点之后 每轮按窗口裁剪后进消息序列
会话摘要 State 字段 conversation_summary 压缩触发时滚动更新（memory/summarizer.py:7-8） 替代被覆盖的旧消息
长期事实 独立 memories.sqlite：entities / facts / task_conclusions（memory/long_term.py:1-7） 反思验证过的候选，任务收尾时写（graph/memory.py:791-798） 按作用域召回，进动态快照
中期向量 Chroma，可选依赖，默认关闭（config.py:293-299） 同上 按相似度召回
常驻记忆 MEMORY.md / USER.md 文件，正文即真源（memory/curated.py:1-10） memory 工具写入 会话开始时冻结，进稳定系统前缀

三层的开关各自独立，取值散在 config.yaml 的 memory 段：短期默认开、 长期默认开、中期默认关（要先装可选依赖）（config.py:281-299、config.py:315-321）。

2 召回：三层汇合，但互不牵连

召回节点把中期与长期汇到同一个 memory_refs，但一层打不开只丢这一层： 各自判断启用、各自捕获异常，失败记一条错误事件而不是静默回退；两层都关时直接透传， 连库和 embedding 模型都不加载（graph/memory.py:215-221）。

中期（向量）的判定顺序是固定的（memory/recall.py:3-9）：

  1. 作用域精确过滤：只用本次可见的 (scope, scope_key) 查询，不把别的项目或工作区的私有记忆混进来。
  2. 相似度下限：低于 min_score 的不召回。
  3. 排序分数：相似度 × 作用域系数 × 重要度系数 × 时间衰减 × 置信度。
  4. 取 top_k 条，按分数倒序。

一个容易改坏的点：min_score 卡在语义相似度上，不是卡在四个系数相乘后的分数上。 系数都 ≤ 1，叠乘会把相关结果整体压到阈值以下，任何配置都会把记忆全筛掉 （memory/recall.py:11-17）。

长期记忆没有向量，所以没有相似度这一步：按作用域过滤后用 confidence × importance 排序， 任务结论没有重要度字段，按有效重要度 1.0 处理（memory/recall.py:27-33）。 自动老化在召回时实时生效，不是等维护任务跑——否则维护之前，超期事实仍会以满分被召回 （memory/recall.py:35-38）。

3 压缩压的是窗口，不是记录

触发口径只有一条公式：估算 prompt tokens / (context_window_tokens − max_tokens) ≥ trigger_ratio， 默认 0.8（graph/nodes.py:512-514、config.py:361-362）。 估算量覆盖实际出站的完整 Prompt：系统提示（含 AGENTS、会话摘要、召回记忆）、消息窗口， 以及工具模式下绑定给模型的工具定义——只估消息会低估一大截（graph/nodes.py:513-514）。

  • 不删消息。只压缩送模型的窗口，Checkpoint 里的 messages 一条都不删（graph/nodes.py:510、memory/short_term.py:3-4）。
  • 摘要替代旧消息。摘要成功后把覆盖边界记进 summary_covered_messages，窗口从该边界之后开始，并按新窗口与新摘要重算预算——否则每轮重发同一批历史，压缩反而让 Prompt 变长（graph/nodes.py:516-518）。
  • 不切开工具调用对。窗口按完整轮次裁剪，再向前对齐到人类消息边界；对齐只让窗口变大，不产生"调用没有结果"的残缺序列（memory/short_term.py:9-13）。
  • 长任务还有一层工具步裁剪。只有一个人类轮次的长工具循环靠轮次裁剪压不动，所以要按"最近工具步"再收一次，更早的整步省略并用一条说明占位（memory/short_term.py:20-24）。

降级口径写得很细，因为它决定页面上"看起来没动静"是不是正常（graph/nodes.py:520-531）：

  • compression.enabled=false：只统计预算，不裁剪、不摘要。
  • 没有更早的消息可摘要（典型是第一轮）且仍在预算内：静默跳过，不记错误、不改计数。
  • 已经超出预算（比值 ≥ 1）却压不动：记一条可见告警，不额外丢消息——窗口最后一轮就是当前问题，丢它等于丢用户诉求。
  • 摘要生成失败：只记错误事件，不改摘要与计数，本轮继续用裁剪后的窗口。

4 两个"压不动"的坑，与它们对应的参数

第一个坑是保底把窗口占满：preserve_recent_turns 默认 8 轮是硬编码条数， 窗口很小时它等于"整段历史都留下"，触发也压不动，而且完全没有信号 （config.py:366-368）。所以加了 retain_ratio（默认 0.16）： 实际保留轮数 = 8 轮之内、且 token 不超过 0.16 × context_window 的最近轮数，下限 1 轮 （config.py:369-372）。配置层还校验保留比例必须小于触发比例， 否则配置阶段就失败，不等运行时压不动（config.py:410-424）。

第二个坑是缓存代价：早先只按工具步条数省略，一个 20 步的循环从第 4 步起每步重写窗口中段， 前缀缓存整段失效。实测命中率只剩 19.9%（同类工具 67.6%），未命中输入 635,714 token， 折合约 ¥1.6 / 次提问（config.py:379-383）。改成字符预算驱动后：

  • tool_step_budget_chars 默认 160,000：短循环一个字都不省，历史保持追加式；只有真正超预算的长循环才从最早的步骤开始省（config.py:385-387、config.py:403）。
  • preserve_recent_tool_steps 默认 3，保留为下限：预算再紧也至少留这么多步（config.py:373-376）。
  • 验收观测量是逐调用缓存读的回落次数（目标 0~1 次），不是命中率（config.py:402）。

5 唯一会写回 Checkpoint 的压缩结果

有一条例外必须单独讲：tool_result_keep_chars（默认 8,192）在上下文已经有压力时， 会把超长的工具正文裁成"头 + 尾 + 标记"，并且把替换结果存进 Checkpoint，预算下降后也不重新展开历史 （config.py:404-407）。替换以 tool_output_overrides 的形式随 State 走 （graph/nodes.py:615-616）。

所以准确的说法是：摘要不删消息；工具正文的裁剪是另一条路径，它保留消息本身、 只覆盖出站与展示用的文本。两者都不是"把历史改成另一个样子"。

6 常驻记忆：每轮必到，所以预算必须小

MEMORY.md 与 USER.md 与前三层的区别是每轮必到而不是按需召回， 因此上限按字符而不是 token，且默认与参照实现一致：memory_char_limit 2200、 user_char_limit 1375（config.py:335-350）。 两个都关时 memory 工具不注册，两块也都不注入 （config.py:352-355、tools/tool_registry.py:182-184）。

存储层有三条硬约束（memory/curated.py:3-14）：

  • 正文是真源：文件就是权威副本，不是库内记录的导出；读失败必须报错，不能当成"空"再回写——那会把用户已有内容抹掉。
  • 上限只校验一次写入的最终结果：溢出时拒绝并回传当前条目，由模型在同一次调用里删旧/缩短再加；加载时超限只告警、不截断。
  • 失败要能解释：外部漂移（文件被手改成没有分隔符的整段）时拒绝覆盖并留 .bak；命中注入模式时拒绝写入。

进提示时是会话开始时冻结的快照，所以模型本轮刚写入的条目本轮看不到。 这一点必须写进段落说明里，否则它会以为写入失败、反复重试（context/prompt_context.py:441-450）。 段落顺序（memory → user）也固定，因为它在稳定前缀里，改序等于让已缓存的前缀整段失效 （context/prompt_context.py:96-98、context/prompt_context.py:453-464）。

7 为什么压缩不改写原始记录

两个理由，一个是审计，一个是能力边界。审计：删改历史会破坏"原文恢复"，也让"这一轮到底看到了什么"无法复查； 记忆写入那条路径同样明写"messages 保持原始记录不动"（graph/memory.py:809-811）。 能力边界：压缩是"这一轮带什么"的决定，它不该顺带变成"曾经发生了什么"的改写——那是两件不同的事， 混在一起后任何一次压不动都会变成数据损坏。

代价是库只增不减。清理交给另一条路径：过期、自动老化与人工删除都在遗忘逻辑里处理 （memory/long_term.py:18-22、memory/recall.py:35-38），压缩不负责删数据。

未验证的部分：压缩的触发时刻、缓存回落的实际次数、常驻记忆注入后的真实效果，本轮只读源码。 验证方法：用一个长会话连续追问，观察 context_budget 的 usage_ratio 与 triggered；再看逐调用的 cached_tokens 是否只在交界处回落。 中期向量层默认关闭，开启需要先装可选依赖（uv sync --extra memory，见 memory/medium_term.py:44-45）。
