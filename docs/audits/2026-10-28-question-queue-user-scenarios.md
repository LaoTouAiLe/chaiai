## 结论

6 个浏览器场景：4 个通过、2 个失败。队列失败场景单独复跑一次，仍然失败。相关 5 个前端测试文件的 93 项测试全部通过，说明下面两个缺陷没有被既有组件/状态测试覆盖。

发现两个问题：

1. **P1：后台接受请求后的状态窗口会让队列抢跑并暂停。** 初始请求返回 HTTP 200、`status=running`；队首消息随后收到 HTTP 409、`SESSION_BUSY`。此时从真实 `/api/tasks` 读取的原任务仍然是 `running`。当前自动发送判断只看快照派生的 `running`，提交钩子虽然等待刷新，但没有消费命令结果的 `running` 来覆盖旧空闲快照。消息没有丢，但队列停在“已暂停”，需要手动继续。位置：`frontend/src/app/LiveApp.tsx:574`、`frontend/src/api/queries.ts:548`；后台返回口径见 `src/local_agent/application/service.py:3164`。
2. **P2：提问答复提交失败后，刷新会丢失答案。** 提交前已经保存的答案，在 HTTP 503 后仍显示于当前卡片；刷新后题组仍等待回答，但文本变成空。`QuestionCard.tsx:110` 在服务端确认前就调用 `clearDrafts`。应在成功确认后清理；失败保持草稿。位置：`frontend/src/features/question/QuestionCard.tsx:110`。

## 浏览器场景步骤

1. **排序/删除与自动发送**：发起 `QUEUE_START`，暂缓该提交响应，让用户连续排入 A、B、C；删除 B，把 C 上移、下移、再上移，核对队列为 C、A；释放提交响应，检查实际 HTTP 提交与队列收口。排序/删除步骤成功，自动收口失败；请求时间线证明原任务仍在运行时 C 已发出。
2. **容量与刷新**：排入 20 条，提交第 21 条，核对提示及草稿；刷新确认待发队列清空。
3. **失败与重试**：将自动发送的下一条响应设为 503，核对消息仍在队首并暂停；继续发送，核对同一个幂等键和成功提交。
4. **题组完整回答**：第一题选测试环境，第二题填分支，返回与刷新后核对答案；第三题选择备份，提交一次；读取会话快照核对全部答案。
5. **整组跳过**：先输入文字，再全部跳过；读取快照确认没有保留答案。
6. **答复失败与刷新**：填写答案，将答复请求设为 503；刷新后断言答案仍在。当前断言失败，输入框为空。
